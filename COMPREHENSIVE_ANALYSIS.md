### 2.4 Anti-Patterns Detected

1. **God Class**: `LaptopRepairManager` (line 529, ~435 lines) does everything — UI creation, event handling, data loading, notification logic, date updates. It is the textbook god class.

2. **God File**: `app.py` at 993 lines with 5 classes is too large. Each dialog class could be its own file.

3. **CSS-in-Code**: ~60 lines of Qt stylesheet strings embedded inside Python methods (`init_ui`, `create_header`, `create_toolbar`) cannot be changed without code modification.

4. **Dead Import**: Line 30 `from services.calculations import calculate_invoice` — imported but never called in `app.py`. Only `table_service.py` uses it, and `invoice_calculator.py` duplicates its logic.

5. **Swallowed Exceptions**: Line 939 `except: pass` in `check_notifications()` silently drops all date-parsing errors.

6. **Duplicate Calculation Logic**:
   - `services/calculations.py` — raw math, returns tuple
   - `services/invoice_calculator.py` — dict wrapper around identical math

## 3. CURRENT ARCHITECTURE ASSESSMENT

### 3.1 Architectural Pattern

The project uses a **loose Service-Layer architecture** trending toward MVC:

```
app.py (Controller + View) 
    ↕ calls
services/* (Business Logic)
    ↕ uses
core/* (Domain Primitives)
    ↕ uses
core/storage/* (Data Access)
```

- **Model**: `repairs.json` + in-memory `self.repairs` list
- **View**: `app.py` classes (QMainWindow, QDialogs) + `ui/table_renderer.py`
- **Controller**: `LaptopRepairManager` methods (add/edit/delete/search/filter)
- **Service Layer**: `services/*` — pure functions operating on data dicts

However, the Controller and View are still tightly fused in `LaptopRepairManager`.

### 3.2 Quality of Existing Modularization

- **Good**: `core/status.py` (constants), `core/filters.py` (pure functions), `core/storage/repairs_storage.py` (single responsibility), `services/repair_service.py` (clean CRUD)
- **Adequate**: `services/invoice_calculator.py`, `services/table_service.py`, `ui/table_renderer.py`
- **Needs Work**: `services/invoice_generator.py` at 538 lines mixes HTML templates with business data; the two functions are nearly identical in structure
- **Broken**: `repair_manager/` skeleton package — mostly empty files with no wiring

## 6. DATABASE/DATA LAYER ANALYSIS

### 6.1 Data Access Pattern

Simple **JSON file persistence** — no real database:

```
app.py (load_data / save_data)
    → core/storage/repairs_storage.py (RepairsStorage)
        → repairs.json (on disk)
```

- **Read**: On startup, `LaptopRepairManager.__init__()` calls `self.load_data()` → `RepairsStorage.load_all()`
- **Write**: After every CRUD operation, `save_data()` → `RepairsStorage.save_all()`
- **Format**: JSON array of repair dicts, persisted with `ensure_ascii=False, indent=4`

### 6.2 Data Layer Separation

- ✅ `RepairsStorage` class in `core/storage/repairs_storage.py` cleanly encapsulates file I/O
- ❌ Error handling is inconsistent: `load_all()` re-raises exceptions, but `app.py` catches them with `QMessageBox`. Some places (`check_notifications`) use bare `except: pass`
- ❌ The storage layer has no type validation, no migration, no backup mechanism

### 6.3 All Database Operations & Locations

| Operation | Where | Line |
|-----------|-------|------|
| `load_all()` | `core/storage/repairs_storage.py` | 10 |
| `save_all()` | `core/storage/repairs_storage.py` | 27 |
| `load_data()` (delegates) | `app.py` (LaptopRepairManager) | 946 |
| `save_data()` (delegates) | `app.py` (LaptopRepairManager) | 954 |
| Shop config load | `ShopSettingsDialog.load_settings()` in `app.py` | 247 |
| Shop config save | `ShopSettingsDialog.save_settings()` in `app.py` | 268 |

**Note**: Shop settings use **direct JSON I/O** in `app.py` lines 250-265 and 281-284, bypassing the `RepairsStorage` abstraction. This means there are two separate persistence mechanisms in `app.py`.
